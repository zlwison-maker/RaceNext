# RaceNext Accommodation Monetization Spec

Version: 1.0
Status: Active MVP accommodation decision spec
Last Updated: 2026-07-31

---

# 1. Scope

本文定义 RaceNext MVP V2 的第一个商业闭环：

```text
赛事搜索流量
↓
赛事页面
↓
住宿决策模块
↓
酒店平台点击
↓
联盟收入
```

当前优先验证：

> 酒店住宿商业化。

但 RaceNext 不是酒店推荐网站。

RaceNext 的核心价值不是展示酒店库存、比较酒店价格或替代酒店平台，而是帮助跑者解决：

> 参加这场赛事，我应该住在哪里最方便？

酒店平台只是最终交易出口。

---

# 2. Product Positioning

新的模块定位：

> Accommodation Decision Layer

中文可称为：

> 住宿决策层。

目标：

> 帮助跑者根据赛事场景选择住宿区域。

它不是：

- 酒店列表。
- 酒店搜索引擎。
- 酒店价格比较平台。
- 酒店库存系统。
- 酒店点评系统。

核心问题：

> 我参加这场比赛，住哪里最方便？

住宿决策层优先回答：

- 哪个区域离起点更近？
- 哪个区域交通更稳？
- 哪个区域更适合外地跑者？
- 哪个区域更适合家属同行？
- 预算有限时应该住哪里？
- 冲成绩用户如何减少赛前交通不确定性？

酒店平台入口只在用户理解住宿区域之后出现。

# 3. MVP Execution Principles

## AI First

优先使用 AI 生成和整理内容。

AI 负责：

- 分析赛事位置。
- 识别住宿区域候选。
- 整理不同用户场景的住宿建议。
- 将结构化数据转为页面内容。
- 生成 FAQ 中的住宿问题。

AI 只能解释已有数据。

AI 不能创造事实数据，包括：

- 虚构区域。
- 虚构距离。
- 虚构交通时间。
- 虚构价格。
- 虚构酒店。
- 虚构官方合作关系。

## Data First

优先使用：

- 官方公开信息。
- 地图数据。
- 酒店平台公开信息。
- 已有赛事数据。

RaceNext 不从零人工维护住宿内容。

## Low Operation Cost

新增一个赛事页面时，住宿模块主要通过：

```text
数据输入
+
AI 生成
+
人工快速审核
```

完成。

避免：

- 每个赛事长期人工运营。
- 手工维护大量酒店。
- 维护酒店实时价格。
- 维护酒店库存。
- 追踪具体酒店房态。

# 4. MVP Page Structure

模块名称：

> 赛事住宿指南

页面结构：

1. 推荐住宿区域。
2. 住宿选择建议。
3. 酒店平台入口。

## 4.1 推荐住宿区域

这是住宿模块的核心。

RaceNext 优先推荐区域，而不是直接推荐酒店。

核心字段：

- 区域名称。
- 距赛事地点距离。
- 到起点预计时间。
- 交通便利程度。
- 价格水平。
- 推荐理由。

可选字段：

- 到终点预计时间。
- 到领物点预计时间。
- 到高铁站 / 机场预计时间。
- 是否适合家属同行。
- 是否适合赛后旅行。

区域类型：

- 起点附近。
- 终点附近。
- 起终点之间。
- 领物点附近。
- 高铁站附近。
- 机场交通便利区域。
- 市中心。
- 景区或赛事小镇附近。
- 地铁 / 公交便利区域。

区域卡片示例：

```text
区域：起点附近

距赛事地点距离：约 1-3 公里
到起点预计时间：步行或打车更稳定
交通便利程度：高
价格水平：中高
推荐理由：适合第一次参赛或冲成绩用户，赛前通勤不确定性更低。
```

## 4.2 住宿选择建议

住宿选择建议由 AI 生成，人工审核。

根据以下用户场景生成：

- 第一次参赛。
- 外地跑者。
- 冲成绩用户。
- 家属同行。
- 预算有限。

建议示例：

```text
如果你第一次参加这场比赛，优先选择起点附近区域。它能减少赛前交通不确定性，尤其适合需要早起集结的跑者。

如果你预算有限，可以选择交通便利但离起点稍远的区域。重点确认比赛当天是否能稳定到达起点。
```

规则：

- AI 只能解释区域、距离、交通、价格水平等已有数据。
- 不生成“最便宜”“一定有房”“官方推荐”等不可控表述。
- 不把住宿建议写成泛旅游攻略。
- 不制造消费焦虑。

## 4.3 酒店平台入口

酒店平台入口是商业出口。

支持：

- 携程。
- 美团。
- 飞猪，如后续可接入。

RaceNext 不维护酒店库存。

RaceNext 不设计酒店价格比较。

RaceNext 不承诺实时价格、最低价或可订房态。

入口层级：

1. 赛事级住宿入口。
2. 区域级酒店平台入口。
3. 酒店级入口，仅当第三方动态数据可稳定提供时考虑。

MVP 优先：

> 区域级酒店平台入口。

原因：

- 符合“先决策区域，再跳转预订”的用户路径。
- 不需要 RaceNext 维护酒店库存。
- 运营成本低。
- 更适合规模化生成。

# 5. Affiliate Provider Layer

RaceNext 需要新增 Affiliate Provider Layer 的产品抽象。

目标：

> RaceNext 与联盟平台解耦。

不要在 RaceNext 自身产品规范中设计：

- 酒店 ID。
- 实时价格。
- 房态库存。
- 佣金比例。
- 酒店排序算法。
- 酒店点评体系。

这些属于第三方酒店平台能力。

RaceNext 只维护住宿决策数据。

示例结构：

```json
{
  "event": {
    "eventId": "race-id",
    "name": "赛事名称"
  },
  "accommodationArea": {
    "areaName": "起点附近",
    "distance": "约 1-3 公里",
    "transportation": "步行或打车更稳定",
    "priceLevel": "中高",
    "reason": "适合第一次参赛或冲成绩用户，赛前通勤不确定性更低。",
    "suitableUsers": ["第一次参赛", "冲成绩用户"]
  },
  "providerLinks": [
    {
      "provider": "ctrip",
      "trackingUrl": "https://example.com"
    }
  ]
}
```

联盟平台负责：

- 用户跳转。
- 酒店搜索。
- 酒店库存。
- 实时价格。
- 订单归因。
- 佣金结算。

RaceNext 负责：

- 赛事场景理解。
- 住宿区域决策。
- 用户场景建议。
- 链接点击追踪。
- 后续行为分析。

# 6. SEO Content Layer

赛事住宿模块不仅是功能模块，也是 SEO 内容资产。

RaceNext 核心流量来源是中国大陆搜索生态：

- 百度。
- 搜狗。
- 360 搜索。
- 微信搜索。
- 微信公众号。

不要以 Google SEO 作为 MVP 主要设计方向。

住宿模块需要支持高商业意图搜索。

典型搜索词：

- 2026上海马拉松住宿推荐。
- 上海马拉松住哪里。
- 崇礼168越野住宿。
- 马拉松酒店推荐。
- 越野比赛住宿攻略。
- 赛事名称 + 住宿。
- 赛事名称 + 酒店。
- 赛事名称 + 住哪里。

## 6.1 SEO Objective

目标：

> 用住宿决策内容承接有明确预订意图的搜索流量。

SEO 内容不应是泛攻略。

它必须围绕：

- 赛事名称。
- 比赛地点。
- 起点。
- 推荐住宿区域。
- 不同用户场景。
- 酒店平台入口。

## 6.2 Title

Title 应自然覆盖赛事名称和住宿决策意图。

示例：

```text
2026上海马拉松住宿指南：起点附近、市中心、高性价比区域推荐
```

Title 原则：

- 包含赛事名称。
- 包含“住宿指南”或“住哪里”。
- 包含 1-3 个核心区域或用户决策点。
- 不堆砌关键词。

## 6.3 Meta Description

Meta Description 目标：

> 描述 RaceNext 如何帮助跑者选择比赛住宿区域，并提供酒店预订入口。

示例：

```text
RaceNext 帮你选择上海马拉松住宿区域，比较起点附近、交通便利区和高性价比区域，适合第一次参赛、外地跑者和预算有限用户，并提供酒店平台入口。
```

## 6.4 H1 / H2 Structure

H1 示例：

```text
2026上海马拉松住宿指南
```

H2 示例：

- 比赛住哪里最方便？
- 起点附近住宿推荐。
- 交通便利区域推荐。
- 预算有限住宿选择。
- 常见住宿问题 FAQ。

H2 原则：

- 围绕用户真实搜索问题。
- 先解决住宿区域决策，再给平台入口。
- FAQ 面向报名后、赛前准备、住宿预订等高意图问题。

## 6.5 SEO Content Rules

允许生成：

- 区域推荐摘要。
- 住宿选择建议。
- 住宿 FAQ。
- 酒店平台入口说明。

不允许生成：

- 虚构酒店。
- 虚构最低价。
- 虚构实时房态。
- 伪官方合作信息。
- 与赛事无关的旅游软文。

# 7. Affiliate Click Tracking Layer

目标：

> 验证住宿模块商业价值。

MVP 不应直接跳转第三方链接。

所有酒店平台入口统一经过 RaceNext 跳转层。

用户路径：

```text
用户点击“查看附近酒店”
↓
RaceNext tracking URL
↓
第三方联盟链接
↓
统计点击行为
```

Tracking URL 示例：

```text
/go/hotel?eventId=shanghai-marathon-2026&areaId=start-area&provider=ctrip&source=event_page_area_card
```

## 7.1 Required Parameters

MVP tracking URL 至少包含：

- `eventId`。
- `areaId`。
- `provider`。
- `source`。

可选参数：

- `placement`。
- `recommendationType`。
- `utmSource`。
- `utmCampaign`。

## 7.2 Click Data

需要记录：

- 哪个赛事产生点击。
- 哪个住宿区域产生点击。
- 哪个平台产生点击。
- 点击时间。
- 页面来源。
- 推荐类型，如果有。

MVP 阶段不要求订单数据。

优先验证：

> 用户是否愿意通过 RaceNext 寻找住宿。

核心指标：

> Hotel CTR。

## 7.3 Provider Redirect

RaceNext tracking URL 负责：

- 记录点击事件。
- 解析 provider。
- 找到对应第三方联盟链接。
- 跳转到第三方平台。

第三方平台负责：

- 酒店搜索。
- 实时价格。
- 库存。
- 预订。
- 后续订单归因。

RaceNext 不在跳转层中处理：

- 酒店库存。
- 酒店价格。
- 佣金比例。
- 订单状态。

# 8. Accommodation Score Model

Accommodation Score 是内部模型。

它不是用户展示评分。

不要在页面中展示：

- 住宿评分。
- 区域评分。
- RaceNext 打分。
- 星级化区域排序。

评分用于：

- 推荐区域排序。
- AI 生成建议。
- 内容生产。
- 规模化时减少人工排序。

总分 100 分。

| Dimension | Weight | Meaning |
|---|---:|---|
| 距离便利 | 40 | 到起点 / 比赛地点是否近，比赛日确定性是否高 |
| 交通便利 | 30 | 高铁、机场、地铁、接驳、主干交通是否便利 |
| 价格水平 | 20 | 是否满足预算有限用户，综合考虑住宿价格和交通成本 |
| 商业价值 | 10 | 是否有较清晰平台入口和可观察点击潜力 |

## 8.1 Distance Convenience - 40

距离优先。

比赛场景下：

> 确定性 > 低价格。

重点看：

- 到起点距离。
- 到比赛地点距离。
- 到终点距离，如果终点不同。
- 到领物点距离，如果领物点影响住宿决策。

## 8.2 Transport Convenience - 30

交通便利性用于判断外地跑者和家属同行的可达性。

重点看：

- 地铁。
- 高铁站。
- 机场。
- 赛事接驳。
- 打车可达性。
- 赛后离开便利性。

## 8.3 Price Level - 20

价格水平不是实时价格。

它是区域级预算判断。

重点看：

- 区域大致价格层级。
- 房源丰富度。
- 价格与交通成本的平衡。
- 是否适合预算有限用户。

## 8.4 Commercial Value - 10

商业价值只作为内部优化因素。

它不能压过用户真实价值。

不得为了更高佣金或更强商业入口，推荐对跑者明显不方便的区域。

重点看：

- 是否有酒店平台可承接。
- 是否有明确区域级搜索入口。
- 是否能产生可追踪点击。

# 9. Accommodation Recommendation Logic

RaceNext 住宿推荐逻辑围绕 4 个核心决策维度。

## 9.1 距离优先

适合：

- 第一次参赛。
- 冲成绩用户。
- 开跑时间早的赛事。
- 起点交通复杂的赛事。

核心：

> 距离起点近。

排序倾向：

- 起点附近。
- 起终点之间。
- 赛事官方接驳点附近。

推荐理由重点：

- 降低赛前迟到风险。
- 减少比赛日交通不确定性。
- 方便赛前热身和装备整理。

## 9.2 交通优先

适合：

- 外地用户。
- 家属同行。
- 赛后需要快速离开的用户。
- 跨城参赛用户。

考虑：

- 地铁。
- 高铁站。
- 机场。
- 接驳交通。
- 市内主干交通。

排序倾向：

- 高铁站 / 机场交通便利区域。
- 地铁沿线区域。
- 赛事接驳点附近。
- 市中心交通枢纽。

推荐理由重点：

- 到达和离开更确定。
- 家属同行出行更方便。
- 适合赛后当天返程。

## 9.3 性价比优先

适合：

- 预算有限用户。
- 学生跑者。
- 多人同行。
- 对赛前通勤容忍度较高的用户。

考虑：

- 价格水平。
- 距离。
- 交通成本。
- 到起点的稳定性。

排序倾向：

- 价格更友好的区域。
- 交通可接受的外围区域。
- 酒店供给更丰富的区域。

推荐理由重点：

- 控制总参赛成本。
- 用交通时间换住宿预算。
- 避免只看房价，不看比赛日通勤。

## 9.4 综合推荐

RaceNext 默认推荐。

结合：

```text
距离
+
交通
+
价格
```

综合推荐适合：

- 不知道如何选择住宿的普通跑者。
- 第一次打开 RaceNext 的用户。
- 需要快速做决策的用户。

排序原则：

1. 比赛日到起点确定性。
2. 交通便利程度。
3. 价格水平。
4. 酒店供给丰富度。
5. 家属同行和赛后旅行便利性。

# 10. Accommodation Decision Model

本文定义产品数据模型，不代表当前要调整数据库。

不要设计：

> Hotel Model。

应设计：

> Accommodation Decision Model。

最小结构：

```ts
type AccommodationDecision = {
  eventId: string;
  areas: AccommodationArea[];
};

type AccommodationArea = {
  areaId?: string;
  areaName: string;
  distance?: string | null;
  transportation?: string | null;
  priceLevel?: "low" | "medium" | "high" | "mixed" | null;
  suitableUsers: string[];
  recommendationReason: string;
  accommodationScore?: AccommodationScore;
  providerLinks: AffiliateProviderLink[];
};

type AccommodationScore = {
  distanceConvenience: number;
  transportConvenience: number;
  priceLevelScore: number;
  commercialValue: number;
  total: number;
};

type AffiliateProviderLink = {
  provider: "ctrip" | "meituan" | "fliggy" | "other";
  trackingUrl: string;
};
```

字段说明：

- `eventId`：关联赛事。
- `areaId`：住宿区域本地标识，用于点击追踪和区域排序。
- `areaName`：住宿区域名称。
- `distance`：区域到赛事地点或起点的距离描述。
- `transportation`：交通便利性和到达方式描述。
- `priceLevel`：价格水平，不是实时价格。
- `suitableUsers`：适合用户场景。
- `recommendationReason`：推荐理由。
- `accommodationScore`：内部排序分，不展示给用户。
- `providerLinks`：酒店平台跳转入口。

扩展字段可包括：

- `distanceToStart`。
- `distanceToFinish`。
- `distanceToPacketPickup`。
- `transportConvenienceLevel`。
- `recommendationType`：distance_first / transport_first / value_first / balanced。
- `sourceNotes`。
- `reviewStatus`。
- `updatedAt`。

不进入本模型：

- 酒店 ID。
- 酒店库存。
- 实时房价。
- 酒店评分。
- 酒店评论。
- 佣金比例。

# 11. AI Production Pipeline

新的流程：

```text
赛事基础数据
↓
AI 分析赛事位置
↓
AI 生成住宿区域候选
↓
Accommodation Score 排序
↓
结合地图 / 公开数据验证
↓
AI 生成住宿决策内容
↓
生成 SEO 内容
↓
人工审核
↓
发布
```

## 11.1 赛事基础数据

输入：

- eventId。
- 赛事名称。
- 比赛日期。
- 城市。
- 比赛地点。
- 起点。
- 终点。
- 集合地点。
- 领物地点。
- 开跑时间。
- 官方来源链接。

如果缺少比赛地点或起点，不生成住宿决策内容。

## 11.2 AI 分析赛事位置

AI 任务：

- 判断赛事地点类型：城市中心、景区、郊区、县城、山地、度假区。
- 判断住宿决策重点：距离、交通、性价比或综合。
- 生成需要验证的区域候选。
- 输出需要地图数据验证的字段。

## 11.3 AI 生成住宿区域候选

AI 基于已有赛事地点和城市结构生成候选区域。

要求：

- MVP 阶段每个赛事最多 3 个住宿区域。
- 城市马拉松一般生成 3 个区域。
- 越野 / 景区赛事一般生成 2-3 个区域。
- 每个区域必须绑定推荐类型。
- 每个区域必须说明适合用户。

## 11.4 Accommodation Score 排序

AI 生成区域候选后，使用 Accommodation Score 做内部排序。

排序步骤：

1. 按距离便利、交通便利、价格水平、商业价值分别打分。
2. 计算总分。
3. 保留最多 3 个区域。
4. 标记每个区域的推荐类型。
5. 输出需要人工重点审核的低置信度字段。

规则：

- 商业价值不得覆盖用户真实便利性。
- 分数不展示给用户。
- 分数只用于排序、内容生产和人工审核辅助。

## 11.5 结合地图 / 公开数据验证

验证内容：

- 区域是否真实存在。
- 区域到起点距离是否合理。
- 区域到高铁站 / 机场 / 地铁 / 接驳点是否合理。
- 区域是否有住宿供给。
- 价格水平是否能从酒店平台公开信息中大致判断。

未验证字段不能作为确定性事实展示。

## 11.6 AI 生成住宿决策内容

AI 只解释已验证或已有数据。

生成内容：

- 区域推荐理由。
- 第一次参赛建议。
- 外地跑者建议。
- 冲成绩用户建议。
- 家属同行建议。
- 预算有限建议。
- 住宿 FAQ。

禁止：

- 创造事实。
- 生成具体未验证酒店。
- 生成具体实时价格。
- 声称官方推荐。
- 声称一定有房。

## 11.7 生成 SEO 内容

基于住宿决策内容生成：

- Title。
- Meta Description。
- H1。
- H2。
- 住宿 FAQ。

要求：

- 面向百度、搜狗、360 搜索、微信搜索和公众号。
- 自然覆盖“赛事名称 + 住宿 / 酒店 / 住哪里”。
- 不以 Google SEO 为主要设计方向。
- 不写成泛旅游攻略。
- 不堆砌关键词。

## 11.8 人工审核

人工负责审核，不负责长期生产。

审核内容：

- 赛事地点是否可信。
- 区域是否合理。
- 距离和交通描述是否明显错误。
- 价格水平表达是否保守。
- 推荐理由是否与赛事场景一致。
- 联盟入口是否正常。
- 是否存在不当商业承诺。

审核策略：

- First5：100% 审核。
- First20：P0 赛事 100% 审核。
- 扩展阶段：高流量赛事全量审核，低风险赛事抽检。

# 12. Commercial Validation Metrics

第一阶段不优先关注订单收入。

原因：

- 联盟归因和结算链路可能存在延迟。
- 初期样本量不足，订单收入不稳定。
- 先验证用户是否愿意通过 RaceNext 寻找住宿。

第一阶段优先关注：

- 赛事页面 PV。
- 住宿模块曝光率。
- 酒店入口点击率 CTR。

## 12.1 Core Metrics

赛事页面 PV：

> 用户是否通过搜索进入赛事页面。

住宿模块曝光率：

> 用户是否看到住宿决策内容。

酒店入口 CTR：

> 用户是否愿意从 RaceNext 跳转到酒店平台。

## 12.2 Secondary Metrics

可记录但不作为第一阶段成功判断核心：

- 区域入口点击分布。
- 不同赛事类型 CTR。
- 不同推荐类型 CTR。
- Provider 点击占比。
- 联盟转化。
- 订单收入。
- 单赛事收入。

## 12.3 MVP Validation Thresholds

建议初步判断：

- 页面 PV 持续增长，说明赛事搜索流量可承接。
- 住宿模块曝光率稳定，说明模块位置和页面结构可用。
- 酒店入口 CTR 达到可观察水平，说明用户愿意通过 RaceNext 寻找住宿。

订单收入进入第二阶段再作为核心指标。

# 13. Scale Design

目标：

> 从 First5 扩展到 First20，再扩展到 500 个赛事时，人工成本不线性增长。

自动化程度：

- 自动读取赛事基础数据。
- 自动生成住宿区域候选。
- 自动拼接区域级 providerLinks。
- 自动生成住宿建议。
- 自动生成住宿 FAQ。
- 自动标记缺失地点、异常距离和不可用链接。

AI 参与环节：

- 赛事位置分析。
- 区域候选生成。
- 用户场景建议。
- 推荐理由生成。
- FAQ 生成。
- 异常提示。

人工审核环节：

- 核验关键地点。
- 核验区域合理性。
- 抽查距离和交通描述。
- 检查价格水平表述。
- 检查 providerLinks 可用性。
- 检查是否存在夸大或硬推。

数据维护策略：

- RaceNext 维护住宿决策数据，不维护酒店库存。
- 区域推荐按赛事周期复核。
- 酒店平台负责实时价格、库存和订单。
- 点击和转化数据反哺区域排序。
- 赛后沉淀住宿点击表现，为未来赛事消费模型提供输入。

# 14. Long-Term Evolution

住宿决策层只是 Commerce Layer 的第一个模块。

未来扩展路径：

```text
Accommodation
↓
Transportation
↓
Equipment
↓
Insurance
```

最终：

```text
Commerce Layer
+
Decision Layer
↓
Personalized Race Decision Agent
```

住宿决策层会积累：

- 用户对不同住宿区域的点击偏好。
- 不同赛事类型的住宿需求强弱。
- 城市马拉松和越野赛事的消费差异。
- 用户是否更偏好距离、交通、性价比或综合推荐。
- 哪些赛事更容易产生酒店平台跳转。

这些数据未来可以反哺：

- 赛事参赛成本估算。
- 赛事消费模型。
- 赛事决策模型。
- 个性化赛事推荐。

长期 RaceNext 可以回答：

> 这场赛事不只是适不适合你跑，也包括住宿、交通和预算是否适合你。

# 15. MVP Constraints

MVP 阶段每个赛事最多展示：

> 3 个住宿区域。

不要做：

- 酒店列表。
- 酒店比较。
- 酒店价格展示。
- 酒店评分。
- 用户评论。

原因：

这些属于酒店平台能力，不是 RaceNext 核心价值。

MVP 住宿模块目标：

> 帮助用户完成“我应该住哪里？”

而不是：

> 帮助用户决定“我应该订哪一家酒店？”

酒店平台入口只承担交易跳转。

RaceNext 的资产是住宿决策数据和用户点击行为。

---

# 16. MVP Definition Of Done

一个赛事住宿指南可进入 MVP 发布评估前，应满足：

- 有可信赛事地点或起点。
- 至少 2 个推荐住宿区域。
- 最多 3 个推荐住宿区域。
- 每个区域包含区域名称、距离或交通描述、价格水平、推荐理由。
- 每个区域标注适合用户。
- 至少 1 个酒店平台入口。
- providerLinks 可追踪。
- 点击经过 RaceNext tracking URL。
- SEO Title、Meta Description、H1/H2 和住宿 FAQ 已生成或明确不展示。
- AI 生成内容经过人工审核。
- 不维护酒店库存。
- 不展示实时价格。
- 不展示酒店列表。
- 不展示酒店比较。
- 不展示酒店评分。
- 不展示用户评论。
- 不承诺最低价。
- 不声称官方推荐。

First5 必须 100% 人工审核。

First20 上线后每周复盘：

- 赛事页面 PV。
- 住宿模块曝光率。
- 酒店入口 CTR。
- 区域点击分布。
- Provider 点击分布。
