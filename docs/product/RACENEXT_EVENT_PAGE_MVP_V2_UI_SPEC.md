Status: Active MVP V2 development spec
Last Updated: 2026-07-31

# 1. Page Positioning

页面名称：

> RaceNext Event Service Page

当前 MVP 定位：

> 热门赛事 SEO 流量入口 + 参赛消费服务入口。

它不是：

- 普通赛事详情页。
- 赛事百科。
- 赛事攻略。
- 完整赛事决策系统。
- 酒店推荐网站。
- 酒店导购网站。
- AI 赛事决策页。

它是：

> 帮助已经决定参赛的跑者，高效完成报名后的住宿和参赛准备的一站式入口。

核心问题：

> 用户搜索赛事进入页面后，如何快速确认赛事，并完成住宿决策？

当前商业验证路径：

```text
用户搜索赛事进入页面
↓
确认赛事信息
↓
获取参赛住宿建议
↓
点击住宿联盟入口
↓
验证商业转化
```

长期 RaceNext 会成为赛事决策顾问，但 MVP V2 不优先解决：

> 我应该跑哪场比赛？

MVP V2 优先解决：

> 我已经决定跑这场比赛，住哪里最方便？

---

# 2. User Task Analysis

核心用户：

> 已经搜索某个赛事名称的高意图跑者。

默认假设：

- 用户已经知道这场赛事。
- 用户大概率已经决定参加或正在准备参加。
- 用户不是来阅读赛事百科。
- 用户最需要快速确认赛事信息和解决住宿问题。

主要任务：

1. 确认这是我要找的比赛。
2. 查看比赛时间、地点、报名状态和组别。
3. 判断参加这场比赛住哪里最方便。
4. 点击酒店平台入口继续查看住宿。
5. 查看 FAQ，解决报名、住宿和参赛准备中的常见疑问。
6. 如果有兴趣，再查看下一场推荐。

页面不承担：

- 个性化赛事选择。
- 训练计划生成。
- AI 适合度判断。
- 复杂赛事难度分析。
- 完整赛事攻略。
- 赛事百科阅读。

# 3. Information Architecture

MVP V2 页面结构：

1. Hero / Event Overview
2. 赛事核心信息
3. 参赛住宿指南
4. FAQ
5. 下一场推荐

删除独立主模块：

- 报名指南。
- 赛事攻略。
- AI参赛指南。
- AI决策卡。
- 训练建议。
- 复杂个性化推荐。

说明：

- 报名状态保留，但并入 Hero / Event Overview 和赛事核心信息。
- 报名入口如有真实来源，可以作为辅助 CTA，但不作为当前商业闭环主模块。
- 当前页面主路径围绕住宿商业化，不继续扩展赛事百科和 AI 决策内容。

模块顺序原则：

- 先让用户确认赛事。
- 再展示最小必要赛事事实。
- 然后快速进入核心商业模块：住宿决策。
- FAQ 承接 SEO 长尾问题。
- 下一场推荐保留长期增长入口，但不抢主任务。

缺失真实数据的字段默认隐藏。

不要为了填充页面生成虚构内容。

# 4. Module Specs

## 4.1 Hero / Event Overview

目标：

> 快速理解赛事，并确认页面匹配用户搜索意图。

包含：

- 赛事名称。
- 比赛时间。
- 比赛地点。
- 赛事类型。
- 报名状态。
- 核心图片。

UI 重点：

- 第一屏必须明确展示赛事名称。
- 图片应服务赛事识别和运动氛围。
- 报名状态要清晰，但不要压过赛事名称。
- 移动端首屏应能引导用户继续查看赛事核心信息和住宿指南。

不要展示：

- 复杂决策信息。
- AI 生成难度。
- 虚构评分。
- 用户评分。
- 星级评价。
- 无来源热度标签。

## 4.2 赛事核心信息

目标：

> 帮助用户确认“这是我要找的比赛”。

本模块不是帮助用户决定是否参加赛事。

保留字段：

1. 赛事名称。
2. 比赛时间。
3. 比赛地点。
4. 报名状态。
5. 赛事组别。

赛事组别必须保留。

示例：

```text
组别：
- 168K
- 100K
- 50K
- 30K
```

保留赛事组别的原因：

- 不同组别影响用户报名选择。
- 不同组别影响比赛准备。
- 不同组别影响住宿时间。
- 不同组别影响装备需求。
- 越野赛事中组别是用户确认赛事信息的重要字段。

当前 MVP 不展示：

- 起终点。
- 累计爬升。
- 赛道详情。
- 报名费用。
- 详细路线。
- 历史成绩。

删除原因：

- 这些信息不是 SEO 用户进入页面后的主要商业需求。
- 当前页面核心不是完整赛事百科。
- 过多赛事细节会稀释住宿商业模块。

UI 重点：

- 信息应可快速扫描。
- 移动端适合使用紧凑信息块。
- 组别应清晰展示，避免被隐藏在长文本中。
- 不展示无法核验的难度、评分或 AI 判断。

## 4.3 参赛住宿指南

目标：

> 回答“参加这场比赛，我应该住哪里最方便？”

这是 MVP V2 核心商业模块。

它不是：

- 酒店列表。
- 酒店比较。
- 酒店评分。
- 酒店价格展示。
- 酒店评论区。

RaceNext 负责：

```text
赛事场景理解
+
住宿区域推荐
+
用户决策辅助
```

联盟平台负责：

- 酒店详情。
- 价格。
- 库存。
- 订单。
- 佣金结算。

连接平台：

- 携程联盟。
- 飞猪联盟。
- 美团联盟。

MVP 阶段每场赛事最多展示 3 个住宿区域。

每个区域包含：

- 区域名称。
- 推荐理由。
- 适合用户。
- 核心优势。
- 查看住宿 CTA。

区域示例：

```text
1. 起点附近

适合：
首次参赛、追求比赛便利

优势：
距离近、减少比赛当天风险

CTA：
查看附近酒店
```

```text
2. 交通便利区域

适合：
外地跑者、家属同行

优势：
机场、高铁、公共交通方便

CTA：
查看住宿选择
```

```text
3. 性价比区域

适合：
预算有限用户

优势：
价格友好

CTA：
查看附近酒店
```

## 4.4 FAQ

目标：

> 承接 SEO 流量，并回答报名、住宿和参赛准备中的高频问题。

内容围绕：

- 报名问题。
- 住宿问题。
- 参赛准备问题。

FAQ 不应扩展为赛事攻略文章。

UI 重点：

- FAQ 结构应支持搜索引擎理解。
- 问题文案贴近用户真实搜索。
- 答案必须基于真实信息，未知则说明未知或隐藏。

## 4.5 下一场推荐

目标：

> 保留长期增长入口。

MVP 处理：

- 简单展示。
- 不作为核心转化模块。
- 不依赖复杂推荐算法。
- 不影响住宿模块的注意力。

未来进入 Decision Layer 后再增强：

- 个性化下一场推荐。
- 相似赛事推荐。
- 适合用户能力的赛事推荐。

# 5. Accommodation Module Design

## 5.1 Module Position

参赛住宿指南应放在：

```text
Hero / Event Overview
↓
赛事核心信息
↓
参赛住宿指南
```

原因：

- 用户先确认赛事。
- 用户看到最小必要赛事事实后，立刻进入住宿判断。
- 住宿模块是当前商业核心，不能放到 FAQ 后或页面底部。
- 页面不应让赛事百科或攻略内容阻挡住宿模块曝光。

如果赛事已进入赛前准备期，住宿模块可以在 Hero 后通过锚点或提示提前引导。

## 5.2 User Flow

用户浏览路径：

```text
赛事信息
↓
时间 / 地点 / 报名状态 / 组别确认
↓
住宿需求产生
↓
选择住宿区域
↓
点击“查看附近酒店”
↓
RaceNext tracking URL
↓
携程 / 飞猪 / 美团
```

页面设计应让用户自然完成：

> 先判断住哪里，再去酒店平台订。

而不是直接被推到外部平台。

## 5.3 Area Card Design

区域卡片是住宿模块核心 UI。

每个区域卡片包含：

- 区域名称。
- 推荐类型标签：距离优先 / 交通优先 / 性价比优先 / 综合推荐。
- 推荐理由。
- 适合用户。
- 核心优势。
- CTA：查看附近酒店 / 查看住宿选择。

示例：

```text
起点附近
距离优先

适合：第一次参赛 / 冲成绩用户

核心优势：
距离近，减少比赛当天移动风险

推荐理由：
赛前通勤不确定性更低，适合希望把精力留给比赛本身的跑者。

[查看附近酒店]
```

卡片设计原则：

- 最多 3 张。
- 默认第一张为综合推荐或距离优先。
- 不展示 Accommodation Score。
- 不展示酒店名称列表。
- 不展示酒店评分。
- 不展示酒店价格。
- 不展示用户评论。

## 5.4 CTA Design

主 CTA：

> 查看附近酒店

可选 CTA：

- 查看住宿选择。
- 去携程查看。
- 去美团查看。
- 去飞猪查看。

CTA 原则：

- 按区域出现，而不是全页面随机出现。
- 必须和推荐理由相邻。
- CTA 文案服务用户任务，不写成广告。
- 不使用“官方酒店”“最低价”“限时抢”等不可控或误导文案。
- 点击必须经过 RaceNext tracking URL。

## 5.5 Affiliate Entry Design

联盟入口是商业出口，不是广告位。

跳转路径：

```text
用户点击 CTA
↓
/go/hotel?eventId=...&areaId=...&provider=...&source=...
↓
第三方联盟链接
```

必须记录：

- eventId。
- areaId。
- provider。
- source。
- 点击时间。
- 页面来源。

MVP 不要求：

- 订单数据。
- 实时佣金数据。
- 酒店库存。
- 酒店价格。

商业化原则：

- RaceNext 不维护酒店库存。
- RaceNext 只负责赛事场景理解、住宿区域推荐和用户决策辅助。
- 携程、飞猪、美团等联盟平台负责酒店详情、价格、库存、订单和佣金结算。

# 6. SEO Design

RaceNext Event Service Page 需要支持中国大陆搜索生态：

- 百度。
- 搜狗。
- 360 搜索。
- 微信搜索。
- 微信公众号。

不要以 Google SEO 为主要设计方向。

## 6.1 SEO Page Structure

页面需要支持：

- Title。
- Meta Description。
- H1。
- H2。
- FAQ 结构。

重点关键词组合：

```text
赛事名称 + 住宿
赛事名称 + 酒店
赛事名称 + 住哪里
赛事名称 + 住宿推荐
赛事名称 + 酒店推荐
赛事名称 + 住宿指南
```

示例 Title：

```text
2026上海马拉松住宿指南：起点附近、市中心、高性价比区域推荐
```

示例 Meta Description：

```text
RaceNext 帮你选择上海马拉松住宿区域，比较起点附近、交通便利区和高性价比区域，适合第一次参赛、外地跑者和预算有限用户，并提供酒店平台入口。
```

示例 H1：

```text
2026上海马拉松住宿指南
```

示例 H2：

- 比赛住哪里最方便？
- 起点附近住宿推荐。
- 交通便利区域推荐。
- 预算有限住宿选择。
- 常见住宿问题 FAQ。

## 6.2 FAQ Structure

FAQ 应覆盖：

- 报名问题。
- 住宿问题。
- 参赛准备问题。

住宿 FAQ 示例：

- 参加这场比赛住哪里最方便？
- 第一次参赛建议住哪里？
- 外地跑者住哪里交通更方便？
- 预算有限应该住哪个区域？
- 可以直接在 RaceNext 订酒店吗？

回答原则：

- 先给区域建议。
- 再解释原因。
- 最后给酒店平台入口。
- 不承诺实时价格和房态。

# 7. Responsive Design Principles

页面必须 Mobile First。

主要使用场景：

- 微信搜索。
- 微信公众号。
- 手机浏览。
- 赛前临时查询。

同时支持桌面端。

## 7.1 Mobile

移动端原则：

- 第一屏必须清楚展示赛事名称、日期、地点和报名状态。
- 住宿模块不能埋太深。
- 区域卡片单列展示。
- CTA 按钮尺寸适合拇指点击。
- 文案短、强扫描。
- 避免复杂表格。
- 避免密集多列信息。

住宿模块移动端建议：

- 区域卡片纵向排列。
- 每张卡片只保留核心信息。
- 详细解释可以折叠。
- CTA 固定在卡片底部。

## 7.2 Desktop

桌面端原则：

- 赛事基础信息和报名状态可以形成上方概览。
- 住宿区域卡片可使用 2-3 列布局。
- 页面右侧可以保留轻量目录或住宿快捷入口。
- 不使用后台管理风格。

## 7.3 Visual Direction

视觉方向：

> 现代运动品牌风格。

参考感受：

- Strava 的运动数据感。
- Nike Running 的动势和清晰 CTA。
- Apple Fitness 的干净、现代、高级。

但 RaceNext 应保持自己的品牌，不照搬。

视觉原则：

- 移动优先。
- 简洁。
- 高级。
- 运动感。
- 时尚。
- 信息清楚。
- 商业入口自然。

不要：

- 黑白后台风。
- 工具网站感。
- 低质信息站风。
- 复杂攻略长文风。
- 大量广告 banner。
- 过度卡片堆叠。

# 8. Commercial Metrics Design

页面设计需要服务商业验证。

核心指标：

1. 赛事页面 PV。
2. 住宿模块曝光率。
3. 酒店入口 CTR。

## 8.1 Event Page PV

设计目标：

> 用户通过赛事搜索进入页面。

对应设计：

- 清晰赛事名称。
- 搜索友好的 Title / H1。
- 结构化 FAQ。
- 最小真实赛事基础信息。

## 8.2 Accommodation Module Exposure

设计目标：

> 用户能看到住宿模块。

对应设计：

- 住宿模块放在赛事核心信息之后。
- 页面顶部可提供“住宿指南”锚点。
- Hero 或核心信息后可提示“建议尽早确认住宿区域”。
- 移动端避免住宿模块被长篇内容淹没。

## 8.3 Hotel Entry CTR

设计目标：

> 用户愿意从 RaceNext 点击到酒店平台。

对应设计：

- 每个区域卡片有清晰 CTA。
- CTA 与推荐理由相邻。
- 文案强调用户任务：查看附近酒店。
- Provider 入口明确但不硬推。
- 不展示无上下文广告。

# 9. Data Principles

遵循：

```text
AI 生产优先
+
现有公开数据优先
+
减少人工维护
```

不要设计：

- 大规模酒店数据库。
- 人工维护酒店列表。
- 酒店评分体系。
- 酒店价格系统。

MVP 阶段重点维护：

- 赛事地点。
- 起点位置。
- 城市交通信息。
- 住宿区域规则。

# 10. MVP Scope

MVP 做：

- Event Service Page。
- Hero / Event Overview。
- 最小赛事核心信息。
- 参赛住宿指南。
- 最多 3 个住宿区域。
- 区域级住宿建议。
- 酒店平台入口。
- RaceNext tracking URL。
- FAQ。
- 简单下一场推荐入口。

MVP 不做：

- 独立报名指南主模块。
- AI 参赛指南。
- 赛事攻略。
- 复杂 AI 决策卡。
- 个性化训练计划。
- 复杂推荐算法。
- 起终点展示。
- 累计爬升展示。
- 赛道详情。
- 报名费用展示。
- 详细路线。
- 历史成绩。
- 酒店列表。
- 酒店价格展示。
- 酒店评分。
- 酒店评论。
- 酒店比较。
- 大规模酒店数据库。
- 人工维护酒店列表。
- 酒店评分体系。
- 酒店价格系统。

删除 / 降低优先级原因：

- 当前数据不足。
- 内容生产成本高。
- 不直接验证住宿商业转化。
- 容易偏回 Decision Layer。
- 不是 SEO 用户进入页面后的主要商业需求。

# 11. Future Decision Layer

未来 RaceNext Event Service Page 可以演进为：

```text
Event Service Page
↓
Decision Layer
↓
Personalized Race Agent
```

未来可增强：

- AI 参赛指南。
- 赛事攻略。
- 适合人群分析。
- 不建议人群。
- 难度判断。
- 个性化下一场推荐。
- 个性化训练建议。
- 完整参赛规划。

住宿模块未来可成为赛事决策的一部分：

- 参赛预算判断。
- 住宿难度判断。
- 外地参赛成本估算。
- 家属同行友好度。
- 目的地赛事推荐因子。

长期目标：

> RaceNext 不只是告诉用户这场比赛在哪里，也能判断这场赛事的住宿、交通、预算和准备成本是否适合用户。
